aireview

A code reviewer that lives in your terminal. You make some changes, type one command, and it reads your changes, finds problems, and even writes your commit message. It all runs on your own machine, with no cloud and no API key. And there's no fancy agent either: it's just Python calling a local model, step by step.

Three ideas carry the whole app. Chaining splits one big job into small LLM calls. The context window limits what each call is allowed to see. Structured output makes each reply safe to hand to the next step. Learn these and the code is just wiring.

Structured output

Don't parse the model's prose. Make it fill in a form.

The problem

A model answers in free text. Even "reply in JSON" can come back wrapped in chatter, with a missing key, or with "severity": "kinda bad". Your code then breaks on a string it can't trust.

The fix, in two layers

  • Constrain. Pass the schema as format=. Ollama restricts what the model can emit to JSON that fits it.
  • Validate. Pydantic checks the reply: types, allowed values, ranges, lengths. Fail once and we retry once, then raise a clear error.
  • Pin the randomness. temperature: 0 makes the model pick its most likely tokens, so the same diff gives (nearly) the same review. A reviewer you can't repeat is a reviewer you can't debug or compare across prompt edits.

Why it matters

Everything after the call is ordinary Python on a real object: review.risk_score, f.severity in SERIOUS. No regex, no json.loads guesswork.

Watch out: structure guarantees shape, not truth. A perfectly valid risk_score: 3 can still be a wrong judgement. Field descriptions are sent to the model too, so they are part of the prompt.

The context window

The model has a fixed amount of working memory. Prompt and reply share it.

The problem

A window is measured in tokens (about 2.5 to 3 characters of code each). Your system prompt, the diff and the model's answer all have to fit. Ollama's default window is small and it truncates silently, so the model reviews half a diff and sounds sure of itself.

What this app does about it

  • Set it on purpose. num_ctx = 16,384 and num_predict = 2,048 in config.py.
  • Budget it. Reserve 4,096 tokens for prompt and reply. The diff gets the rest, worked out from NUM_CTX so the numbers can't drift apart.
  • Spend it well. Drop lockfiles and binaries, put source files before docs, cap each file at 3,000 characters so one huge file can't hide the rest.
  • Narrow it per step. The fix advisor only sees diffs of the files with serious findings.
  • Say what was cut. Trimmed and dropped files are recorded, so the user knows when a review was partial.
Watch out: a bigger window isn't free. It costs memory and time, and models pay less attention to the middle of long prompts. Sending less, better chosen, usually beats sending more.

LLM chaining

Several small calls beat one giant prompt.

The problem

Ask a small local model to review, plan fixes and write a commit message in one go and every part gets worse. The prompt is huge, the output schema is tangled, and when something's off you can't tell which part failed.

The pattern

  • One job per call. Each step has its own prompt file and its own schema.
  • Typed handoff. Step 1's ReviewResult is the input to steps 2 and 3. Nothing is re-parsed in between.
  • Plain Python decides the route. if serious: is a normal if, not an agent. It's cheap, predictable and easy to debug.
  • Each step sees only what it needs. That keeps every context small (see the previous idea).
Watch out: errors compound. A bad step 1 feeds a bad step 2, which is why every handoff is validated and --trace shows each prompt and reply.

Observability

If you can't see the prompt, you can't fix the answer.

The problem

A chain has several model calls, and the final output hides what each one saw and said. When the commit message is wrong, was it the diff, the prompt, the review from step 1, or the model?

What this app does

  • One place to record. Every model call goes through ask(), so one line there logs all of them to TRACE.
  • Everything that shaped the reply. System prompt, user prompt, options, schema name, raw reply.
  • Cost and health. Prompt and output token counts, seconds, and done_reason.
  • Two ways to read it. --trace prints it (long prompts cut for the screen), --trace-file saves the full JSON. The file is also written when a run fails.
Watch out: the trace holds your code diff. Treat a saved trace file like source code before you share it.

Fail loudly, degrade honestly

A confident answer built on partial input is the worst outcome.

The problem

Models always sound sure. If Ollama is down, the diff was cut, or the reply was truncated, a quiet fallback gives the user a review that looks complete and isn't.

What this app does

  • Check early. check_model confirms Ollama is running and the model is pulled before any work, with the exact command to fix it.
  • Clear errors. Git and model problems become GitError / LLMError with a plain message. The CLI shows it on the failing row and exits 1, with no stack trace.
  • Bounded waits. A 120 s request timeout and a reply cap (num_predict) stop a rambling model from hanging the tool.
  • Bad output is an error. A cut-off or malformed reply fails validation, retries once, then raises instead of guessing.
  • Say what wasn't seen. Trimmed and unreviewed files are listed. A clean result on a partial diff reads "no issues in the part the model saw", never a green tick.
  • Exit codes for scripts. 1 = error, 2 = risk over --fail-on-risk. With --json, warnings go to stderr so stdout stays clean JSON.
